## 第一章：编译器到底解决什么问题

### 1.1 源程序、目标程序与语义保持

计算机语言是表达计算的工具。程序员写的源程序贴近人的思维习惯：变量、表达式、函数、循环；处理器执行的则是某个指令集上的机器指令。Compiler 的任务，是把一种语言写的程序翻译成另一种语言的程序，并且保留原程序规定的行为。

这里的“等价”是语义上的要求，看的是行为，而不是生成的代码长得像不像。源表达式规定先乘后加，翻译结果就必须体现这个结构；语言规定了某种类型转换，编译器就必须实现它。优化阶段可以调整指令顺序、删除重复计算，前提是在语言语义之下保持可观察行为。正确永远排在快之前。

把源程序记为 $p$，翻译结果记为 $C(p)$，输入记为 $x$，编译正确性可以写成：

$$
\operatorname{Behavior}_{src}(p,x)
=\operatorname{Behavior}_{tgt}(C(p),x).
$$

这个式子是一个简化的写法。真实语言还有异常、输入输出和不终止的程序，需要更丰富的语义模型来描述。但它抓住了要点：编译正确性比较的是执行行为，不是程序文本。翻译的终点也不一定是机器码，把一种高级语言翻成另一种高级语言同样是编译。

### 1.2 Compiler 与 Interpreter

两份导出用“先翻译、后执行”刻画 Compiler，用“边读边执行”刻画 Interpreter。作为入门图景这很好用：Compiler 产出一份交给下一环节的目标表示，Interpreter 直接完成输入程序描述的计算。

工程上的系统往往两种方式都用。Java 和 Python 的常见实现先把源码编译成 Bytecode，再由虚拟机解释执行；运行时 JIT 编译器还会把热点代码编译成本机代码。所以“编译型”“解释型”描述的是某个实现在某一层的做法，而不是语言本身的属性。讨论时先说清楚是哪一层。

翻译与执行是否分开，和“能不能提前报错”也是两个问题。Compiler 能在运行前发现一部分错误；Interpreter 同样可以先做解析和静态检查。两者都会遇到只有运行时才能暴露的问题，比如除零或数组越界。

### 1.3 从源文件到运行中的进程

原生代码的常见工具链是：Preprocessor → Compiler → Assembler → Linker → Loader。不同语言和实现会省略、合并或调整其中的环节。

| 环节 | 主要输入 | 主要输出 | 解决的问题 |
|---|---|---|---|
| Preprocessor | 带预处理指令的源文本 | 展开后的源文本 | 宏替换、条件编译等 |
| Compiler | 源程序 | 汇编或其他目标表示 | 把语言结构映射到目标结构 |
| Assembler | 汇编程序 | 可重定位目标文件 | 把助记符转成指令编码 |
| Linker | 目标文件与库 | 可执行文件或共享库 | 连接定义和引用、重定位 |
| Loader | 可执行文件 | 已装入地址空间的程序 | 为执行建立运行环境 |

举个例子：一个源文件调用了另一个文件里定义的函数。Compiler 处理第一个文件时，只能生成一个带“外部引用”标记的目标文件；把这个引用和函数定义连起来是 Linker 的工作。所以单个文件编译通过，整个程序未必能链接成功。`undefined reference` 是典型的链接错误，少写分号则是语法错误，二者发生在不同环节。

## 第二章：六个逻辑阶段与同一个表达式

### 2.1 用一个例子串起全流程

考虑一个教学语言里的赋值语句：

```text
result = base + factor * 24
```

假定 `result`、`base`、`factor` 都已声明为数值变量，语法规定乘法优先于加法。下面每到一个阶段，都问两个问题：这一步的输入是什么结构？输出比输入多知道了什么？

源文本只是一串字符。字符本身不会告诉我们 `factor` 是一个标识符，也不会告诉我们乘法应当是加法的子结构。编译器一步步把这些信息恢复出来，再把结构转成便于后续处理的表示。下图把这条语句在六个阶段中的样子并排画了出来。

![编译器的六个逻辑阶段：同一条语句在每一步变成什么](/images/compiler-midterm/pipeline.svg)

从左往右看，每一步的输出都比上一步多一层信息：词法分析给出了“这是什么词”，语法分析给出了“谁是谁的子结构”，语义分析给出了“每个子结构是什么类型”，中间代码把树拆成了线性的简单操作，后面两步则面向目标机器。底部的符号表贯穿所有阶段。

### 2.2 Lexical Analysis：字符变成 Token

Lexer 从左到右扫描字符，切分出有意义的词法单位。上面的语句会变成：

```text
<ID, p_result> <ASSIGN> <ID, p_base> <PLUS>
<ID, p_factor> <MUL> <INT, 24>
```

`ID` 是 Token 类别，`p_result` 可以是指向符号表或字符串表的入口。用指针只是一种实现选择，Token 的属性也可以是别的东西；比如整数可以先保存原始文本，等后面再做数值范围检查。

空白一般只起分隔 Token 的作用，不作为普通 Token 交给 Parser；注释通常也在这一层被跳过。换行是否有意义由语言决定：Python 的缩进和换行就是语法结构的一部分，这类语言的 Lexer 要把它们转成专门的 Token。

Lexer 识别出了 `PLUS` 和 `MUL`，但不决定加法和乘法谁嵌套在谁里面——层次关系由后面的语法规则决定。这是区分词法和语法最清楚的一个例子：词法管“这一段是什么”，语法管“这些段怎么组合”。

### 2.3 Syntax Analysis：Token 变成层次结构

Parser 读入 Token 序列，按照 Context-Free Grammar 检查结构，构造 Parse Tree 或更紧凑的语法表示。这条语句的运算结构是：

```text
assign
├── result
└── add
    ├── base
    └── multiply
        ├── factor
        └── 24
```

这棵树实际上是 AST。Parse Tree 还会保留 `Expression`、`Term`、`Factor` 这类文法节点以及括号等终结符；AST 去掉了只服务于语法组织的节点，只留下运算本身。第三篇判断文法二义性时用的是 Parse Tree，两种树要分清。

语法分析能发现 `base + * factor` 这类错误：两个运算符连在一起，按文法无法构成表达式。但如果 `factor` 根本没声明，Token 和句法结构都是合法的，要等到语义检查才会发现。

### 2.4 Semantic Analysis：结构合法还不够

Semantic Analyzer 检查类型、声明、作用域等上下文约束。如果 `factor` 是字符串，而语言没有定义字符串乘整数，那么 AST 能顺利建出来，类型检查却通不过。

同一个名字可以在不同作用域里各有一个声明，某处引用的究竟是哪一个，由作用域规则决定。因此符号表不只是“出现过哪些名字”的清单，它还要支持名字解析和属性查询。

教材里常把语义分析的输出画成带类型标注的语法树。实现上可以直接给已有节点加属性，也可以另建一种中间表示。逻辑阶段描述的是职责划分，不要求每个阶段都对应一个独立的程序模块。

### 2.5 Intermediate Code Generation

三地址码把复杂表达式拆成简单操作：

```text
t1 = factor * 24
t2 = base + t1
result = t2
```

“三地址”指一条指令最多涉及一个结果位置和两个操作数位置，并不要求每条指令真的有三个内存地址。`t1`、`t2` 是编译器引入的临时量，最终可能只占用寄存器。

如果语义要求先把整数常量转成浮点数，中间代码里就要出现这一步转换。可见类型分析和代码生成是连在一起的：前者给后者提供生成正确操作所需的信息。

### 2.6 Optimization 与 Code Generation

Optimizer 对中间表示做保持语义的变换，比如常量折叠、删除可证明无用的计算。`3 * 8` 在合适的语义下可以预先算成 `24`。但“看起来一样”的表达式不一定能合并：副作用、溢出规则和浮点语义都会影响一个变换是否合法。

Code Generator 把操作映射到目标指令，处理寄存器分配、指令选择等问题。期中复习只需要知道它在整体结构中的位置。前两篇的重点，是在源码字符和 Token 之间建立严格的数学模型。

### 2.7 Phase 与 Pass

Phase 是按任务性质划分的逻辑阶段；Pass 是对源程序或中间表示完整处理一遍。一个 Pass 可以完成好几个 Phase，一个 Phase 也可能需要好几个 Pass。[^phase-pass]

最常见的组织方式是：Parser 需要下一个 Token 时才调用 Lexer，而不是让 Lexer 先把整个文件扫完写到磁盘；语义检查也常常和建树交错进行。所以“六个阶段”不意味着“扫描源文件六遍”。考试中的概念辨析题，要把职责划分和实现组织分开回答。

## 第三章：Token、Lexeme、Pattern 的精确定义

### 3.1 三个对象回答三种问题

| 对象 | 回答的问题 | 示例 |
|---|---|---|
| Token 类别 | 这一段在语言里扮演什么角色？ | `ID`、`INT`、`PLUS` |
| Lexeme | 源文件里实际出现了哪些字符？ | `factor`、`24`、`+` |
| Pattern | 哪些字符串可以属于这一类别？ | 字母开头、后接字母或数字 |

`count` 和 `index` 是两个不同的 Lexeme，却属于同一个 Token 类别 `ID`。反过来，`if` 的字形完全符合标识符的 Pattern，但语言把它规定为关键字，Lexer 就应返回关键字类别。处理这种重叠靠的是“类别选择规则”（第二篇的最长匹配加优先级），而不是修改 Lexeme 的定义。

Token 常写成 $\langle name,attribute\rangle$：`name` 是类别，`attribute` 携带后续阶段需要的信息。之所以把所有标识符归成一个类别 `ID`，是为了让 Parser 的文法保持有限——如果每个变量名都是一个独立的 Token 类别，文法就要随着程序里的名字无限扩张。

### 3.2 类别识别与属性保存

对 `007`，Lexer 可以返回 `INT`，但原文 `007` 和数值 $7$ 是两个对象。语言可能禁止前导零，报错时也需要原始拼写和源位置。所以一个实用的 Token 往往同时携带类别、原文范围、解析后的属性值和行列号。

源位置看起来是工程细节，却说明了 Lexer 的职责不只是“接受或拒绝一个串”。真正的扫描器要知道每次匹配发生在哪里，才能把错误准确指向源文件。第二篇会把单个自动机的识别推广到“多条 Token 规则同时竞争”的情形。

### 3.3 词法错误、语法错误、语义错误

假设教学语言只允许字母数字标识符和常见算术符号，没有 `@`：

- 遇到 `@`，无法组成任何 Token，是词法错误。
- Token 都能产生，但序列是 `ID PLUS MUL ID`，不符合表达式文法，是语法错误。
- 序列是 `ID PLUS ID`，结构没问题，但两边类型不支持加法，是语义错误。

错误归哪一类，取决于语言规则和实现设计。比如非法的数字后缀，既可以让 Lexer 当成非法词素直接报错，也可以拆成几个 Token 交给后面的阶段拒绝。回答这类题目时，先写出你采用的假设，再说明是哪一层规则发现了错误。

## 第四章：从字符到语言的数学对象

### 4.1 Alphabet、String 与 Empty String

Alphabet $\Sigma$ 是一个有限的符号集合，例如 $\Sigma=\{a,b\}$。这里的“符号”是模型中不可再分的原子，在形式语言的推导中按题目定义的单位来处理。

String 是字母表中符号的有限序列。$w=abba$ 的长度 $|w|=4$。Empty String 记为 $\varepsilon$，$|\varepsilon|=0$。纸面上写的 $\varepsilon$ 表示“一个字符都没有”，它不是一个能被输入的字符。

$\Sigma^n$ 是所有长度为 $n$ 的串的集合，$\Sigma^0=\{\varepsilon\}$。把所有有限长度合在一起：

$$
\Sigma^*=\bigcup_{n\geq0}\Sigma^n,
\qquad
\Sigma^+=\bigcup_{n\geq1}\Sigma^n.
$$

$\Sigma^*$ 一定包含 $\varepsilon$，$\Sigma^+$ 不包含。当 $\Sigma=\{a,b\}$ 时，$\Sigma^*=\{\varepsilon,a,b,aa,ab,ba,bb,\ldots\}$。

### 4.2 Language 是字符串的集合

Language $L$ 是 $\Sigma^*$ 的一个子集，可以有限也可以无限。$\{a,ab\}$ 有两个元素；“所有以 `ab` 结尾的 $a,b$ 串”是无限集合。[^empty-language]

一个必须牢记的区别：

$$
\varnothing\ne\{\varepsilon\}.
$$

左边一个元素都没有；右边有一个元素，这个元素是长度为零的串。正规式、NFA 的终态判断、CFG 的 Nullable 计算都建立在这个区别上，混淆一次会一路错下去。

对任意串 $w$，$w\varepsilon=\varepsilon w=w$。对语言 $L$，$L\{\varepsilon\}=\{\varepsilon\}L=L$，而 $L\varnothing=\varnothing L=\varnothing$。最后这个等式直接用连接的定义就能验证：连接要从两个集合里各取一个元素，空集里取不出元素，结果自然一个串也没有。

### 4.3 语言的三种核心运算

Union：$L_1\cup L_2$ 包含属于任意一边的串。Concatenation：

$$
L_1L_2=\{xy\mid x\in L_1,\ y\in L_2\}.
$$

例如 $L_1=\{a,ab\}$，$L_2=\{b\}$，则 $L_1L_2=\{ab,abb\}$。连接一般不交换：$\{a\}\{b\}=\{ab\}$，而 $\{b\}\{a\}=\{ba\}$。

Closure 定义为 $L^*=\bigcup_{n\ge0}L^n$，其中 $L^0=\{\varepsilon\}$。例如 $\{ab\}^*=\{\varepsilon,ab,abab,\ldots\}$。闭包每次重复的是集合中的一个完整成员：`ab` 作为整体重复，不会被拆成 `a`、`b` 再随意排列。

## 第五章：Regular Expression

### 5.1 语法形式与语言含义

Regular Expression 是描述 Regular Language 的代数记法。表达式本身和它表示的语言是两个对象，用 $L(r)$ 表示正规式 $r$ 的语言。

| 表达式 | 语言含义 |
|---|---|
| $\varnothing$ | 空语言 |
| $\varepsilon$ | $\{\varepsilon\}$ |
| $a$，$a\in\Sigma$ | $\{a\}$ |
| $r\mid s$ | $L(r)\cup L(s)$ |
| $rs$ | $L(r)L(s)$ |
| $r^*$ | $L(r)^*$ |

有的教材用 $+$ 表示选择，有的工具用 `+` 表示“一次或多次”。本系列统一用 $\mid$ 表示选择，用 $r^+$ 表示一次或多次。

### 5.2 优先级与括号

优先级从高到低是：闭包、连接、选择。所以 $a\mid bc^*$ 表示 $a\mid(b(c^*))$，而不是 $(a\mid b)c^*$。处理复杂表达式时，先补全括号、画出运算结构，这棵结构树正是第二篇递归执行 Thompson 构造的依据。

![(a|b)*ab 的运算结构：闭包 > 连接 > 选择](/images/compiler-midterm/regex-tree.svg)

以本系列的主例 $(a\mid b)^*ab$ 为例，最外层是三段连接：先是任意多次的 `a` 或 `b`，再接一个 `a`，最后接一个 `b`。所以它表示所有以 `ab` 结尾的 $a,b$ 串。前面的闭包可以重复零次，因此 `ab` 本身属于这个语言；空串不属于，因为结尾的 `ab` 必须出现。

判断一个串是否属于语言，最可靠的方法是给出分解。`aab` 属于，因为可以分成闭包部分 `a` 加结尾 `ab`；`aba` 不属于，因为它的最后两个字符是 `ba`，找不到任何分解让结尾落在 `ab` 上。

### 5.3 常用缩写

$r^+=rr^*$ 表示至少一次；$r?=(r\mid\varepsilon)$ 表示零次或一次。字符类 `[a-z]` 是一组字符的选择的简写，具体包含哪些字符取决于字符集和正则实现。在课程算法里，把它看成对一组字符的选择即可。

教学用的标识符模式可以写成：

$$
letter(letter\mid digit)^*.
$$

`letter`、`digit` 是事先定义好的字符集合名。这个模式要求首字符是字母，后面跟零个或多个字母或数字：`x`、`x2` 合法，`2x` 不合法。

### 5.4 几个能直接用于检查的等价式

$$
r\mid s\equiv s\mid r,\qquad
(r\mid s)t\equiv rt\mid st,
$$

$$
\varepsilon r\equiv r,\qquad
\varnothing r\equiv\varnothing,\qquad
r^*\equiv\varepsilon\mid rr^*.
$$

$\equiv$ 表示两边描述同一个语言。连接不满足交换律；闭包也不能分配到选择上：$(a\mid b)^*$ 包含 `ab`，$a^*\mid b^*$ 却只含全 `a` 或全 `b` 的串。一个反例 `ab` 就足以否定 $(a\mid b)^*\equiv a^*\mid b^*$。

### 5.5 正规式与编程工具中的 Regex

本课程的正规式恰好描述 Regular Language。实际的正则引擎加入了反向引用等扩展，这些扩展已经超出了有限自动机能识别的范围。手算构造时，只使用选择、连接、闭包三种运算。

同样，任意嵌套的括号结构超出了正规式的能力（第十一章给出证明），需要下一层的 CFG 来描述。由此形成编译器前端的自然分工：正规式描述局部的词法模式，CFG 描述递归的句法结构。

## 第六章：Finite Automata

### 6.1 DFA 的五元组

DFA 记为 $M=(Q,\Sigma,\delta,q_0,F)$：$Q$ 是有限状态集，$\Sigma$ 是输入字母表，$q_0\in Q$ 是初态，$F\subseteq Q$ 是接受状态集。完整 DFA 的转移函数是

$$
\delta:Q\times\Sigma\to Q.
$$

也就是说，每个状态面对每个输入符号，恰好有一个后继。手绘图常常省略通往“拒绝状态”的边，这是部分转移的简写，约定为“缺边即拒绝”。做最小化之前，要先把缺的边补到一个死状态上，得到完整的转移表。

理解 DFA 的关键是：**状态是对已读输入的有限摘要**。DFA 不保存整个输入串，只保存“对判断未来是否接受有用”的那部分信息。设计 DFA 时，先想清楚每个状态代表哪一类已读前缀，再画圆圈和箭头。

### 6.2 读完整个串后再判断接受

把转移函数扩展到字符串上，得到 $\delta^*$：

$$
\delta^*(q,\varepsilon)=q,\qquad
\delta^*(q,wa)=\delta(\delta^*(q,w),a).
$$

DFA 接受的语言是：

$$
L(M)=\{w\in\Sigma^*\mid\delta^*(q_0,w)\in F\}.
$$

判断标准是读完整个串之后停在哪里。途中经过接受状态并不算数。第二篇的 Lexer 会额外“记住最近一次经过接受状态的位置”，那是在连续切分多个 Token 时加上的控制逻辑，DFA 对单个完整串的接受定义保持不变。

### 6.3 一个识别以 ab 结尾的 DFA

为 $(a\mid b)^*ab$ 设计三个状态，每个状态对应一类已读前缀：[^suffix-state]

- $q_0$：已读部分的结尾既不是 `a` 也不是 `ab`（包括空串）；
- $q_1$：已读部分以 `a` 结尾；
- $q_2$：已读部分以 `ab` 结尾。只有 $q_2$ 接受。

| 当前状态 | 读 a | 读 b | 接受？ |
|---|---|---|---|
| $q_0$ | $q_1$ | $q_0$ | 否 |
| $q_1$ | $q_1$ | $q_2$ | 否 |
| $q_2$ | $q_1$ | $q_0$ | 是 |

![DFA：识别所有以 ab 结尾的串 (a|b)*ab](/images/compiler-midterm/suffix-dfa.svg)

每条边都能用状态含义解释。读到 `a`，无论之前在哪，新的结尾都是 `a`，所以三个状态读 `a` 都去 $q_1$。读到 `b`，只有之前以 `a` 结尾才能形成 `ab`，所以只有 $q_1$ 读 `b` 去 $q_2$；从 $q_2$ 读 `b` 得到结尾 `bb`，回到 $q_0$。

读 `aabab` 时，路径为 $q_0\to q_1\to q_1\to q_2\to q_1\to q_2$，最终停在 $q_2$，接受。读 `aba` 时，路径为 $q_0\to q_1\to q_2\to q_1$，中途到过 $q_2$，但最后停在 $q_1$，拒绝。

### 6.4 NFA：允许多个后继和 ε 边

允许 $\varepsilon$ 边的 NFA 同样是五元组，只是转移函数变成：

$$
\delta:Q\times(\Sigma\cup\{\varepsilon\})\to2^Q.
$$

$2^Q$ 是 $Q$ 的幂集，所以转移结果是一个状态集合，可以为空，可以只有一个状态，也可以有多个。$\varepsilon$ 转移不消耗输入；字符转移恰好消耗一个输入符号。

NFA 接受一个串，当且仅当**存在**一条从初态出发、读完这个串后停在接受状态的路径。其他路径失败不影响结果。直觉上，NFA 在每个岔路口都“猜对了”；实现上，我们不去猜，而是同时跟踪所有可能到达的状态。

下图用一个三状态 NFA 识别同一个语言 $(a\mid b)^*ab$。$p_0$ 读 `a` 时有两个选择：留在 $p_0$ 继续循环，或者认为“这个 `a` 就是结尾 `ab` 的开头”而去 $p_1$。

![NFA 的并行运行：候选状态集合](/images/compiler-midterm/nfa-parallel.svg)

下半部分是同时跟踪所有候选状态的过程。读 `aab`：开始时候选集合是 $\{p_0\}$；读第一个 `a`，两个选择都保留，得到 $\{p_0,p_1\}$；读第二个 `a`，$p_0$ 又分出两条路，$p_1$ 没有 `a` 边、这条路死掉，仍是 $\{p_0,p_1\}$；读 `b`，$p_0$ 留在原地，$p_1$ 走到 $p_2$，得到 $\{p_0,p_2\}$。集合中含有接受状态 $p_2$，所以接受。

读 `aba` 时，第二步之后集合里已经有 $p_2$，但第三个字符 `a` 把 $p_2$ 这条路掐断了（$p_2$ 没有出边），最终集合 $\{p_0,p_1\}$ 不含接受状态，拒绝。这和 DFA 的“途中接受不算数”是同一回事。

图中每个候选集合下方标注了它对应的后缀 DFA 状态：$\{p_0\}$ 对应 $q_0$，$\{p_0,p_1\}$ 对应 $q_1$，$\{p_0,p_2\}$ 对应 $q_2$。这不是巧合：把“候选状态集合”本身当作一个状态，NFA 就变成了 DFA。这正是第二篇子集构造的核心思想。

### 6.5 ε-closure：为什么必须包含自己

$\varepsilon\text{-closure}(q)$ 是从 $q$ 出发、沿零条或多条 $\varepsilon$ 边能到达的所有状态。“零条”意味着停在原地，所以 $q$ 一定在自己的闭包里。

对状态集合 $T$：

$$
E(T)=\bigcup_{q\in T}\varepsilon\text{-closure}(q).
$$

后文都用 $E(T)$ 表示这个运算。

![ε-closure：只沿 ε 边，零步也算](/images/compiler-midterm/eps-closure.svg)

图中从 $q_0$ 出发：零步停在 $q_0$；一步到 $q_1$；两步到 $q_2$；$q_2$ 又有一条 ε 边回到 $q_0$，形成环。$q_3$ 需要读 `a` 才能到，所以不在闭包里。读完 `a` 到达 $q_3$ 之后，要再求一次闭包，才能把 $q_4$ 也包含进来。这就是第二篇里 $D(T,a)=E(move(T,a))$ 的由来：先走一步字符边，再把 ε 边走尽。

闭包运算满足 $T\subseteq E(T)$ 和 $E(E(T))=E(T)$。第二个性质给出了一个自检方法：对已经求好的闭包再做一次，不应该出现新状态；如果出现了，说明第一遍没有把所有 ε 路径展开完。

### 6.6 DFA 与 NFA 的能力和代价

Regular Expression、NFA、DFA 描述的是同一类语言，三者表达能力相同，只是形式不同。NFA 转成 DFA 后状态可能变多，因为一个 DFA 状态代表的是一组 NFA 状态。

若 NFA 有 $n$ 个状态，它的子集最多 $2^n$ 个，这是 DFA 状态数的上界。实际构造只生成从初态出发能到达的子集，通常远少于这个上界——上一节的例子里，三状态 NFA 只用到了三个子集。

运行时，DFA 每读一个符号只需查一次表；模拟 NFA 则要维护整个候选集合，每一步对集合里的每个状态都查一次。这是 Lexer 通常把 NFA 先转成 DFA 再运行的原因：把代价从“每次运行”挪到了“构造一次”。

## 第七章：把符号对应到实际操作

### 7.1 本篇符号速查

| 符号 | 含义 | 容易混淆的对象 |
|---|---|---|
| $\Sigma$ | Alphabet | 某个具体字符串 |
| $\varepsilon$ | 长度零的字符串 | 空集合 |
| $\varnothing$ | 没有元素的集合 | $\{\varepsilon\}$ |
| $L(r)$ | 正规式表示的语言 | 表达式文本 |
| $Q$ | 自动机状态集 | 输入字符集 |
| $F$ | 接受状态集 | 可以有多个状态 |
| $\delta$ | 一步转移函数 | 整串转移 $\delta^*$ |
| $2^Q$ | 状态子集的集合 | 数值平方 |
| $E(T)$ | ε 闭包 | 不消耗输入 |

### 7.2 用最短证据检查理解

要否定“两个正规式等价”，只需给出一个只属于其中一边的串；要证明等价，则必须说明任意串在两边的归属都一致，测几个样例不够。

检查自动机时，按这个顺序测：空串；长度一、长度二的边界串；一个途中经过接受状态、最后又离开的串。对“以 `ab` 结尾”的语言，`ab`、`aab`、`babab` 应接受，$\varepsilon$、`a`、`b`、`aba` 应拒绝。每一个结论都应能沿转移表一步步复现出来。

回到编译器结构，可以把同一个程序分别写成字符、Token、AST 和三地址码，并指出每次转换增加了什么信息。做到这一点，本章的主线就掌握了。下一篇不再凭直觉设计 DFA，而是从正规式出发，执行一条可以逐步复查的构造链。

## 第八章：把定义变成推理的四个层次

### 8.1 先确认正在操作哪个集合

初学时最常见的错误，往往不在运算本身，而在把串、语言、状态、状态集合放到同一层讨论。草稿上给每个对象标出类型会很有帮助：`a` 是字符，`ab` 是串，$\{ab\}$ 是只含一个串的语言，$\{q_1,q_2\}$ 是状态集合。它们写法相近，含义完全不同。

例如正规式 $ab$ 的语言是 $\{ab\}$，而 $\{a,b\}$ 是两个长度为一的串组成的语言。连接作用于语言时，从左右两个集合各取一个完整的串，而不是把花括号里的字符摊开重新组合。

子集构造得到的 DFA 状态可以取名为 A，但它在构造过程中的身份是一个 NFA 状态集合。判断两个子集状态是否相同，比较的是集合的成员。最小化时讨论的“两个不同集合对未来输入表现是否相同”，则是另一种关系。

给对象标类型也能帮你读公式。$\delta(q,a)$ 在 DFA 中是一个状态，在 NFA 中是一个状态集合。在 NFA 的公式里，如果把这个集合直接当成单个状态往下传，类型就对不上了。很多“公式记不住”的情况，检查一下每个运算的输入输出类型就能解决。

### 8.2 再用最小边界建立感觉

检查一个语言，先看空串，它能检验闭包的零次重复、空分支以及初态是否接受。$a^*$ 必须接受空串，$aa^*$ 必须拒绝空串——两者只差一个必须出现的 `a`，语言边界就变了。

然后看最短的非空串，再看一个刚好满足模式的串和一个只差一个字符的串。以“以 `ab` 结尾”为例：`ab` 是最短的成功串，`a` 是还没完成，`aba` 是成功之后又被延长而失败。这三个例子正好把“必须读完整串”和“途中到过接受状态”区分开。

随机的长串反而不容易发现问题。自动机漏掉了零次路径，在长串上可能照样接受；漏掉了一条回边，在只重复一次的输入上也可能表现正常。边界输入之所以有效，是因为每一个都专门检验一条构造规则。

### 8.3 然后给出对任意输入成立的解释

测试能发现错误，但证明“对所有输入都正确”需要另一种论证。对 DFA，标准做法是给每个状态写下它代表的前缀类别（称为不变量），再证明每条转移都保持这个不变量。

以后缀 DFA 为例。规定 $q_1$ 代表“以 `a` 结尾的串”，$q_2$ 代表“以 `ab` 结尾的串”，其余的串归 $q_0$。三类互不重叠，合起来覆盖所有串。

- **初始条件**：空串属于 $q_0$ 这一类，DFA 也从 $q_0$ 开始。
- **保持性**：读 `a` 后，任何串都变成以 `a` 结尾，所以都进 $q_1$；读 `b` 后，只有原来以 `a` 结尾的串变成以 `ab` 结尾，所以只有 $q_1$ 去 $q_2$，其余进 $q_0$。
- **最终条件**：接受状态 $q_2$ 恰好对应“以 `ab` 结尾”这一类。

三条合在一起，就证明了这台 DFA 恰好识别目标语言。这比笼统地说“状态保存匹配进度”精确得多，因为它规定了任意一个已读前缀应该落在哪个状态。

### 8.4 最后研究实现选择的影响

同一个语言可以由很多台不同的自动机识别，状态编号也可以随意取。有的 NFA 构造在连接时合并接口状态，有的用 ε 边连接接口，两者都正确，只是中间状态集合会不同，抄答案时不能混用两套编号。

Lexer 实现中常常把字符分组：如果所有数字在每个状态下去向都相同，就让它们共用一列转移。这是表压缩，不是把不同的输入字符在数学上当成同一个符号。一旦某个状态下它们需要不同的去向，就必须拆开。

所以对照参考答案时，图的形状可以不同，但约定必须一致。先写清楚完整的边集合、初态和接受集合，再比较识别的语言，比追求圆圈位置一样有意义得多。

## 第九章：常见表述的精确修正

### 9.1 “NFA 比 DFA 更强”错在哪里

NFA 允许多个后继和 ε 转移，写起来更灵活，构图通常也更方便。但灵活的描述方式不等于更强的识别能力。子集构造能把任何 NFA 转成识别同一语言的 DFA，所以两者能识别的语言类完全相同。

这里实际上混了四件事：描述的长短、状态的数量、每一步的执行代价、语言的表达能力。NFA 可以更紧凑，DFA 执行更快，这些都是表示和实现上的差异。把它们笼统地说成“更强”，后面讲状态爆炸时就说不清了。

### 9.2 “ε 转移就是读一个空字符”错在哪里

输入中不存在“空字符”。ε 转移是自动机内部的状态移动，输入位置原地不动。如果把 ε 当作一个普通字符，自动机就会要求输入里出现一个本不存在的符号，识别的语言随之改变。

可以把运行过程看成两部分：输入位置和当前候选状态集合。走字符边，两者都可能变；走 ε 边，只有状态集合变。这个二维视角解释了为什么闭包要在读字符之前和之后都算一次，而且不会改变已经读过的长度。

### 9.3 “正则闭包会把所有字符任意打乱”错在哪里

对语言做闭包，是把它的成员一个接一个地连接起来，成员内部的字符顺序不变。$\{ab,ba\}^*$ 能产生 `abba`，因为它是 `ab` 接 `ba`；能否产生某个串，要看它能否被切成若干个完整成员，而不是数 `a` 和 `b` 各有几个。

这种“分段”的视角和 NFA 的接受路径是一致的：每穿过一个片段，就消耗一个该片段允许的串；重复就是把若干条合法路径首尾相连。正规式的结构和自动机的结构由此相互对应。

### 9.4 “词法分析只需识别标识符”错在哪里

`ID` 只是众多词法类别之一。常量、关键字、运算符、分隔符，以及按语言规则处理的空白和注释，扫描器都要处理。数字可能带小数点、指数或后缀；字符串字面量涉及转义序列和结束引号。

本系列用最小的例子讲清模式和自动机的关系。面对真实语言时，先查语言规范规定了哪些合法形式，再套用构造算法。算法负责把规范变成自动机，规范本身要由设计者给出。

## 第十章：一份程序在各阶段的错误画像

### 10.1 同一行文本可能有多个问题

考虑文本 `total = amount + @`。`@` 不属于任何合法模式，Lexer 先报告它；Parser 收到的 Token 序列在加号后缺少操作数，可能再报告一次“表达式不完整”。第二个错误是第一个错误引起的连锁反应。

所以“错误属于哪个阶段”不一定是一行文本对应一个标签。更准确的说法是：某条约束由哪个阶段检查，某条诊断在什么处理状态下产生。阅读编译器的报错时，先找到最早的根因，再看后面的连锁错误，往往能快很多。

### 10.2 结构正确不代表名字含义正确

`x = y + 1` 完全符合表达式和赋值的 CFG，但 `y` 可能在当前作用域里没有声明。如果语言要求先声明后使用，语义检查会失败。Lexer 仍然正确地把 `y` 识别为 `ID`——“未声明”是语义层的问题，不是词法层的问题。

也有语言需要借助符号表信息来辅助词法或语法判断，C 语言里区分类型名和变量名就是一例。先掌握分层的职责模型，再看具体实现如何让各层协作，就不会把模型中的分层误当成工程上不可逾越的边界。

### 10.3 目标相关错误与运行时行为

代码生成会受到寄存器、指令集和调用约定的约束；链接时会发现外部定义缺失；运行后还可能出现和输入有关的异常。把这些都叫作“语法错”，就混淆了语言结构、程序语义和执行环境三个层面。

回到本篇开头的语义保持要求：各阶段生成的表示，是同一个翻译任务的不同视角。前端识别并约束源程序的结构，后端把合法结构落实到目标平台。看清这条主线，自动机、文法、类型和代码就串成了一个整体。

### 10.4 本篇结束前的一次口头复述

合上笔记，试着用自己的话讲一遍：字符如何变成 Token，Token 为什么要带属性，Parser 加入了什么层次，为什么还需要语义检查；再说明空串和空语言的区别，按定义读出一个正规式的语言，最后在三状态后缀 DFA 上跑一遍 `aabab` 和 `aba`。

哪一处只能背出结论而举不出最小例子，就回到对应的定义重读。第一篇的作用是建立后面所有算法共用的对象与约定；下一篇的集合运算再复杂，也只是对这些对象执行精确的规则。

## 第十一章：从语言限制理解方法选择

### 11.1 有限记忆与无限输入

DFA 能读任意长的输入，却只有有限个状态。这并不矛盾：它不记住完整历史，只保留和未来判断有关的摘要。判断是否以 `ab` 结尾时，不管已经读了一百个还是一万个字符，只需要知道最后的后缀属于哪一类。

所以有限状态的限制不在输入长度，而在于任务需要区分多少种“历史情境”。判断长度的奇偶只要两个状态；而要记住一个可以任意大的精确计数，有限个状态就不够了。

### 11.2 为什么平衡括号需要另一种结构

考虑任意嵌套深度的平衡括号。读了若干个左括号之后，机器必须知道“还欠几个右括号”：欠一个、欠两个、欠三个……面对同一串右括号，这些情境给出的接受结果各不相同。

用抽屉原理可以证明有限状态做不到这一点。

![状态数有限：任意深度的括号匹配无法用 DFA 识别](/images/compiler-midterm/pigeonhole.svg)

设 DFA 有 $k$ 个状态。考虑 $k+1$ 个前缀：0 个、1 个、……、$k$ 个左括号。状态只有 $k$ 个，所以至少有两个前缀落进同一个状态 $s$，设它们分别有 $i$ 个和 $j$ 个左括号，$i<j$。现在在两者后面都接上 $i$ 个右括号。从同一个状态 $s$ 出发、读同样的后缀，DFA 必然停在同一个状态 $t$。但 $i$ 个左括号加 $i$ 个右括号是平衡的，应当接受；$j$ 个左括号加 $i$ 个右括号还缺右括号，应当拒绝。同一个 $t$ 不能既接受又拒绝，矛盾。

因此任意深度的平衡括号不能由 DFA 识别，也就不能由正规式描述。这个论证依赖“深度无界”：如果规范把嵌套深度限制在某个常数以内，有限状态完全可以枚举所有允许的深度。所以讨论时要先说清楚深度是否有上界。

### 11.3 递归并不意味着无从分析

CFG 可以用 $S\to(S)S\mid\varepsilon$ 这样的产生式描述平衡括号。现在不需要会为它构造预测表，只需注意到：同一个非终结符可以在右部再次出现，因此能表达任意层的嵌套。

后续的 Parser 用一个栈保存尚未完成的层次，栈可以随输入增长，这正是有限状态机缺少的那种记忆。编译原理前半部分的主线由此清晰：先用有限状态识别局部模式，再用文法加栈处理递归结构。

### 11.4 语言层级与编译阶段的对应是松散的

真实语言里，有些词法规则需要额外的状态（比如嵌套注释），也有些上下文约束要在语法分析之后用文法以外的手段检查（比如“变量先声明后使用”）。课程中的分工模型是理解这些工具的起点，具体实现可以在这个基础上调整。

做题时，先读清楚输入字母表、Token 定义、文法和实现假设。如果题目要求支持嵌套注释，这部分就超出了普通正则的能力，需要另行处理；如果题目不要求嵌套，就直接用正则描述。

### 11.5 语言、规范与实现的三层关系

规范决定哪些文本合法、各自是什么意思；数学模型提供可以精确推理的表达；实现把模型变成具体的数据结构和程序。错误可能出在任何一层：规则写错了、算法用错了，或者程序没有忠实地执行算法。

学习时可以分三问：模式是否符合语言要求？构造是否保持了模式的语言？代码是否正确地维护了候选集合和输入位置？这三问分别对应规范、理论和实现，每一层都要单独验证。
